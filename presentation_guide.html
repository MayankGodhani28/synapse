💡 High-Level Project Summary

Synapse is a privacy-first, zero-subscription personal knowledge retrieval engine. It captures web content via a Manifest V3 browser extension, performs dense 384-dimensional vector embedding on-device, indexes information inside a containerized PostgreSQL + pgvector database, and provides grounded Retrieval-Augmented Generation (RAG) with source citations to any connected application.

System High-Level Data Flow

Data Flow Pipeline End-to-End Architecture

  1. Capture Layer: Chrome Manifest V3 Extension extracts clean article text using Mozilla Readability DOM parser.
  2. Ingestion API: Express REST backend (Port 5000) handles payload validation and user authentication.
  3. Processing Layer: 300-word sliding window chunker → Local all-MiniLM-L6-v2 embedding pipeline (produces $\mathbb{R}^{384}$ dense vectors).
  4. Storage Layer: PostgreSQL 16 with pgvector in Docker (Port 5433) indexed via IVFFlat.
  5. RAG & Retrieval: Cosine distance matching ($\Leftrightarrow$), threshold filter ($\ge 0.25$), and citation synthesis.
  6. Consumer Layer: Standalone client application (Port 3001) connected via Bearer API Key handshake.

4. Comprehensive Technology Stack Reference

Here is a brief, highly technical summary of every single tool, language, library, and framework used in Synapse.

1. PostgreSQL 16 & pgvector Extension Database & Vector Math

Role: Core relational and vector storage engine, running inside a Docker container (synapse-db) mapped to host port 5433.

Why Chosen: Instead of running a separate vector database (like Chroma or Pinecone) and a separate SQL database for users, pgvector integrates vector arithmetic directly into standard SQL queries. It supports the Cosine Distance operator (<=>) and L2 distance (<->). We created an IVFFlat index on the 384-dimensional embedding column for logarithmic nearest-neighbor search speeds.

2. Local Embedding Model: all-MiniLM-L6-v2 (@xenova/transformers) NLP Vectorization

Role: Generates dense 384-dimensional vectors from raw text chunks entirely on the host machine.

Why Chosen: Running transformer models locally guarantees 100% user privacy, eliminates network round-trip latency to OpenAI, and avoids API fees. all-MiniLM-L6-v2 is a distilled BERT model fine-tuned specifically for semantic sentence similarity with exceptional accuracy-to-size ratio (~90MB model size).

3. Chrome Extension (Manifest V3) & Mozilla Readability Ingestion & DOM Parsing

Role: Captures web pages and highlighted text directly from the user's browser.

Why Chosen: Manifest V3 adheres to modern browser security standards using background service workers. Mozilla Readability (the same engine powering Firefox Reader View) strips away navigation menus, footers, sidebars, tracking scripts, and advertisements, ensuring only meaningful article text is sent for vectorization.

4. Node.js & Express.js Backend Runtime & REST API

Role: Asynchronous REST backend hosting routes for ingestion (/memory/add), search (/memory/search), RAG chat (/chat), and API key management.

Why Chosen: Node's non-blocking event loop is ideal for handling concurrent I/O requests between database streams, embedding tensor pipelines, and HTTP clients.

5. Sliding Window Chunking Engine Text Preprocessing

Role: Splits long documents into discrete 300-word chunks with a 50-word overlapping stride.

Why Chosen: Embedding models have strict context window limits. Chunking preserves high semantic density, while the overlap guarantees that concepts bridging chunk boundaries are never truncated or lost.

6. Docker & Containerization DevOps & Isolation

Role: Isolates the PostgreSQL 16 + pgvector environment with persistent volume storage (synapse_pgdata).

Why Chosen: Ensures reproducible deployment across Windows, Linux, and macOS without requiring the evaluator to manually install PostgreSQL vector packages or configure native C compilers.

7. SHA-256 API Key Authentication Security & Multi-Tenancy

Role: Secures external API communication for third-party client integrations.

Why Chosen: API keys are generated using cryptographically strong pseudo-random bytes, hashed with SHA-256 before storage in the database, and verified using timing-safe comparisons to prevent timing attacks.

5. Viva Voce & Guide Q&A Master Sheet

Be ready for these common questions from project guides, external examiners, or evaluators.

Q1: "Why did you choose pgvector over specialized vector databases like Pinecone or Milvus?"
Your Answer: "Specialized cloud vector databases like Pinecone introduce three major issues for a personal memory layer: recurring subscription costs, high network latency, and privacy violations from transmitting personal browsing history over the internet. By using PostgreSQL with the pgvector extension, we retain full ACID guarantees, store relational user metadata alongside vectors in a single database, and keep the entire system 100% on-device and free."
Q2: "What index type does your vector database use, and what is its computational complexity?"
Your Answer: "We use an IVFFlat (Inverted File Flat) index with the vector_cosine_ops operator class. Without an index, vector search is $O(N)$, performing a brute-force sequential scan across all vectors. IVFFlat clusters vectors into Voronoi cells (lists). At query time, the search only scans the centroids of the nearest clusters, reducing query complexity to sub-linear time ($O(\sqrt{N})$), allowing queries to return in under 8 milliseconds."
Q3: "How does your system prevent hallucinations when the user asks an unrelated question?"
Your Answer: "We apply a strict dual-guardrail approach. First, we set a mathematical cosine similarity threshold of 0.25. Any database chunks scoring below this threshold are discarded. Second, in our RAG system prompt, the model is strictly instructed to base its synthesis only on verified context chunks and cite them with source tags. If no context meets the threshold, the system provides an honest fallback instead of hallucinating."
Q4: "Why 384 dimensions? Why not 1536 dimensions like OpenAI text-embedding-ada-002?"
Your Answer: "There is a direct trade-off between dimensionality, memory consumption, and CPU inference latency. While 1536-dimensional vectors offer marginal gains on massive corpora, they require 4x the RAM and compute power. all-MiniLM-L6-v2 maps sentences to a 384-dimensional space that captures dense semantic nuances while executing in under 50 milliseconds directly on a standard CPU without needing an expensive GPU."
Q5: "How do you handle multi-tenant data isolation?"
Your Answer: "Every memory and vector record in our database schema is strictly bound to a foreign key user_id. During vector similarity search, the SQL query applies a pre-filter: WHERE user_id = $1 prior to computing the cosine distance operator. This mathematically guarantees that User A can never retrieve or view vectors belonging to User B."
Q6: "What happens if a user saves a 50-page document?"
Your Answer: "Our sliding-window chunking engine breaks the 50-page document into sequential 300-word sub-documents with a 50-word stride. Each chunk is individually embedded and stored in the embeddings table linked to the parent record in the memories table. When querying, only the top 5 most relevant chunks are retrieved, ensuring the LLM's context window is never overloaded."
